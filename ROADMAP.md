# Loom Roadmap

*Decision document. Feature-level backlog lives in [docs/loom-improvements.md](docs/loom-improvements.md); competitive context in [docs/competitive-analysis.md](docs/competitive-analysis.md); scaling verdict in [docs/horizontal-scaling-investigation.md](docs/horizontal-scaling-investigation.md).*

## North Star

Loom is the **shared agentic ecosystem** — the interoperability fabric that makes AI coding tools (claude-code, opencode, goose, crush, jcode, …) composable instead of sileroed. Skills, MCP servers, sessions, auth, hooks, and workflows are written once and shared across every tool. Loom is **not** another agent or another orchestration UI; it is the programmable infrastructure layer those tools and UIs sit on.

## Where We Are (v0.10.2)

A 32-crate Rust workspace (plus the standalone `loom-egress-proxy` image crate): the verified review engine (`loom review`) over ACP-seated reviewers, the container egress allowlist (Docker enforced via the `loom-egress-proxy` sidecar, see `docs/decisions/0002-egress-allowlist-proxy.md`), daemon (`loomd`) + CLI + TUI, Unix-socket IPC, working ACP dispatch with tracked runs, encrypted vault with hash-chained audit, MCP registry with health checks, session export/branch/merge/search, git-worktree parallel execution, GitHub/Linear trackers, SSH remote capture, TOML generic adapters, honest CI (clippy `-D warnings`, 5-job matrix in `.github/workflows/ci.yml`: a 3-entry test matrix, container smoke, integration, benchmarks, security), Homebrew distribution with bottles.

## Pillars

Five pillars, deliberately sequenced: nobody adopts — let alone pays for — infrastructure that breaks. Pillars 1–3 are the product; pillar 4 is the business built on top; pillar 5 is the demand driver that makes the business worth paying for.

### 1. Harden the Core *(v0.9.x → v0.10)* — refine existing features

Fix what exists before building what's next. Evidence: v0.9.3 shipped a five-handler panic class that CI had been greenwashing for months; daemon lifecycle still produced socket races and duplicate daemons (the single-instance lock and the service-unit ownership both landed in v0.9.6).

- **Daemon lifecycle done right.** ~~Single-instance lock (not socket-file-existence checks)~~, ~~stale-socket recovery in `daemon start`~~, ~~CLI↔daemon version handshake over IPC; warn hard on skew~~ — all landed in v0.9.6 (lock in `loom-core::lock`, held for the daemon's lifetime; `doctor` fails on skew, `status` warns). Also landed: **the service unit owns the lifecycle** — loomd now handles SIGTERM/SIGHUP and removes its socket on the way out, the idle shutdown is configurable via `LOOM_IDLE_TIMEOUT_MS` (`0` = disabled), and the launchd/systemd units set it to `0` and restart only on a crash (`KeepAlive{SuccessfulExit:false}` / `Restart=on-failure`) instead of resurrecting a deliberate clean exit. That was the infinite respawn loop (~397 restarts/24h). Also landed: **the CLI routes through the unit** — `loom daemon start`/`stop` go to launchd/systemd instead of spawning a second, competing daemon, `loom daemon install-service` stops a manually started daemon first so the unit can take the single-instance lock, and `loom daemon status` reports the supervisor and its state. Pillar 1's daemon-lifecycle work is closed.
- **IPC protocol hardening.** ~~Versioned request envelope~~, ~~request timeouts~~, ~~panic isolation as a rule (the v0.9.3 scoped-thread pattern)~~ — all landed in v0.9.6. ~~Connection-backoff guidance for CLI~~ — landed: the CLI connects with a bounded backoff (8 attempts, 200ms doubling to a 1s ceiling) instead of trusting the socket file's existence, and an unreachable daemon says what happened and what to type (`daemon socket is stale (loomd is not running) — run \`loom daemon restart\``). The backoff belongs to the commands that *talk* to the daemon (`memory`, `acp`, `thread`); the single-shot probes (`status`, `doctor`, `telemetry`, `daemon status`) stay single-shot — they report the daemon's state and must not wait it out — but they print the same cause-and-remedy advice.
- **Finish-or-delete sweep.** ~~Dead code~~ — the unwired `loomd/src/snapshot_builder.rs` orphan was deleted in v0.9.6, and so was the fake `EmbeddedPane` dispatcher (it never spawned anything): `App::dispatch_embedded_pane` is now the single owner of that path, covered by a test that asserts the `loom workflow dispatch <task> --agent <agent>` command is actually spawned. Every placeholder or unwired feature gets shipped or removed: anything still returning "not yet wired" (VISION.md gap list). Dead code is a lie the roadmap stops telling. (The embedded-pane live-TUI e2e closed 2026-10-25 — driven in a real pty: menu → `e` → pane opens → dispatch spawns → output streams.)
- **Release automation.** ~~One command: version bump → changelog → tag → CI → bottles dispatch.~~ Landed in v0.9.6 as `scripts/release.sh <version>`: it validates the version (semver, strictly greater, no leading zeros), refuses a dirty tree or an existing tag, bumps `[workspace.package]`, writes the changelog section from `RELEASE_NOTES.md`, refreshes and verifies `Cargo.lock`, commits, tags, and prints the exact `gh workflow run` command. The bottles workflow now validates the dispatched version against `Cargo.toml`, so the "wrong `version` input" hazard is closed. `--push` (off by default) pushes and dispatches.
- ~~**Docs coherence.** README/STATUS/VISION drift (subcommand counts, clone URLs, stale STATUS roadmap stub) reconciled into one truth; STATUS.md roadmap section points here.~~ — landed 2026-10-26: README/STATUS/VISION reconciled against the code (`crates/loom-cli/src/cli.rs`, `Cargo.toml`, `.github/workflows/homebrew-bottles.yml`): 32-crate workspace plus the standalone image crate, 37 top-level subcommands, Homebrew-tap and cargo-install wording matched, and the STATUS.md Roadmap section is the two-line pointer here.
- **Test depth.** ~~Daemon-lifecycle integration tests (restart races, socket contention, version skew)~~ — landed in v0.9.6 as `crates/loomd/tests/daemon_lifecycle.rs`, which runs the real `loomd` binary against a throwaway ecosystem dir: the IPC version handshake, a second daemon refusing to start instead of stealing the live socket, SIGTERM stopping the daemon and releasing the lock, and a stale socket left by a crashed daemon not blocking a new one. ### 2. Security & Trust *(v0.10 → v0.11)*

Agents execute arbitrary code with your credentials. Trust is the adoption gate — and the enterprise sales gate.

- **Sandboxed execution.** `loom-runtime` container isolation becomes a first-class, CI-tested path (not just feature-gated compile), with per-run network policy. Default documented; opt-in until proven.
  - *Landed (container path + network posture):* the per-run network posture is now a policy enum (`none` / `restricted` / `unrestricted`) instead of a free-form network name, so the absence of a value can no longer mean "engine default network" (unrestricted egress). The **default posture for a container run is `none`** — no egress — and `unrestricted` is the explicit escape hatch. Container isolation itself stays **opt-in**: the default runtime is still `process`, so no existing run silently loses networking. The posture is documented in `README.md` (§Execution) and in the `loom-runtime` crate docs; the pure-logic policy tests run in the normal CI `test` job, and a new `container` CI job runs the end-to-end container smoke test on `ubuntu-latest` with Docker present. ~~Still open: the egress proxy that turns `restricted` from fail-closed `none` into a real host allowlist.~~ — landed 2026-10-26 via preflight PR2 (`docs/decisions/0002-egress-allowlist-proxy.md`): Docker composes an `loom-egress-proxy` sidecar on an internal user-defined network, the allowlist is enforced (hosts matched as written, CIDR-aware, before any DNS lookup), smoke-proved ALLOWED:200/DENIED:OK; Podman and Kubernetes stay deny-all until their wiring (ADR 0002).
- **Scoped credentials.** Vault already does ChaCha20Poly1305 + ACL + hash-chained audit. Next: per-run, per-tool scoped credentials — an agent gets a derived, revocable grant, never the master key. Key rotation.
  - *Landed (per-run grants):* `loom auth grant issue` issues a **derived**, revocable, expiring token scoped to one provider + tool + run; the agent never holds the stored secret. `loom auth grant verify` checks scope, expiry and revocation; `loom auth grant revoke` takes effect immediately and is audited. The registry (`<loom-dir>/auth/grants.json`) is written `0600`. There is deliberately **no CLI `redeem`** — redemption returns plaintext and belongs to a trusted broker (`AuthManager::redeem_grant`). Trust model and residual risks: `docs/architecture/grant-trust-model.md`.
  - *Landed (key rotation, 2026-10-25):* `loom auth rotate-password` re-encrypts every stored credential under a fresh Argon2id-derived key (`CredentialVault::change_password`, tested roundtrip). Rotation invalidates every derived grant key by design (the grant key mixes the master key), and the command says so.
- ~~**Supply chain.** Plugin Ed25519 verification moves from opt-in (`--verify`) to the default path; key-continuity pinning for registry installs.~~ — landed 2026-10-26 (branch `p12/supply-chain`, ADR `docs/decisions/0005-plugin-verify-by-default.md`): `security.require_signature` defaults **true** — remote URL installs without a signature are refused with the opt-out knob named; local `loom plugin register` stays untouched (own TOML from local disk is not remote supply chain). Trust enforcement moved inside the registry (`install_from_content`/`update` fail closed **before any file write**); key-continuity pins at `{loom_dir}/auth/plugin-pins.json` (0600) — a subsequent install signed with a different key refuses until the pin entry is explicitly deleted. Residual risk (first-contact key theft / TOFU) named in the ADR.
- ~~**Compliance posture.** Audit chain export + documented retention — the SOC2 groundwork pillar 4 depends on.~~ — landed: `loom auth export` writes a verifiable JSON export of the hash-chained audit log. The export is **self-verifying**: every `entry_hash` is re-derived from the exported fields (the chain hash covers the normalised outcome, `chain_scheme: 2`, so the raw `result` never leaves the machine) and the whole document is signed with a per-machine Ed25519 key. `loom auth verify` reports ONE verdict — `intact` (chain re-derives **and** the signature verifies against a pinned public key), `tampered` (a named check failed), or `unanchored` (self-consistent only, because no key was pinned). The retention window is one config knob (`[security] audit_retention_days`, default 365 days, the oldest out-of-window prefix dropped from exports).

### 3. Ecosystem & Protocol *(v0.11 → v1.0)*

Adoption comes from being the easiest layer to plug into. The moat is the protocol, not the adapters.

- **Public protocol.** Versioned, documented spec for the adapter contract and ACP dispatch; publish the `acp_registry` schemas. Third-party agents register without forking.
  ↳ Spec landed: [`docs/protocol/adapter-and-acp-protocol.md`](docs/protocol/adapter-and-acp-protocol.md) (spec v1.0.0 — adapter contract v1, ACP protocol v1). ~~Publishing the `acp_registry` schemas~~ — closed 2026-10-25: the registry vendored at `acp_registry/` is now a real submodule (`.gitmodules` added — a fresh clone populates it with `git submodule update --init`), and the documented `config/acp.toml` `registry_url` setting is live: one owner `acp_launch::registry_url` feeds all three fetch sites (`add-acp-agent`, `acp registry`, launch resolution). Still open: the SDK story below.
- ~~**SDK story.** Grow `loom-ffi` beyond minimal; a thin binding story for registering tools, skills, and handlers from other languages.~~ — landed 2026-10-26 via preflight PR1 (loom-ffi registration exports); `docs/adapter-contribution.md` has the Python ctypes example.
- **Adapter coverage.** More presets (still open); `GenericAdapter` TOML stays the escape hatch; ~~a contribution guide so coverage scales without us~~ — guide landed 2026-10-26 ([docs/adapter-contribution.md](docs/adapter-contribution.md), PR3).
- **Consumption surfaces.** `loom-mcp-server` as the bridge for external orchestrators/UIs to use Loom services — the "UIs consume Loom" play from the competitive analysis.

### 4. Commercialization *(post-1.0, gated on 1–3)*

Market proof exists: Conductor at $50–60/mo/user sells orchestration with cloud execution and less infrastructure depth; Conifer sells the same thesis from the other end — a hosted gateway (drop-in provider-key replacement) monetized by Parallax review episodes. Both validate Loom's defensible wedge: **team-grade shared infrastructure** — the vault, registries, and audit — not another UI.

- **Licensing.** Core stays MIT (it is the adoption funnel). Commercial surface = hosted services + team features under a separate license; no re-licensing the core. *Decision required — see Open Questions.*
- **API key management as a product.** The team vault broker: daemon proxies and scopes every credential agents use, with full audit. loom-auth is already the strongest asset here; productize it.
- **Deployment tiers.** Documented headless daemon for servers/containers; `loom-remote` as the managed-remote story; a hosted control plane (registry sync, relay, fleet status) — **not** hosted scale-out: the scaling investigation's verdict is local-first by design.
- **Team tier.** Shared skill/MCP/template registries with org sync, RBAC on the vault, org-wide audit rollup, usage reporting.
- **Usage metering.** Per-run, per-tool, per-token accounting from the routing/telemetry crates — the honesty layer for both cost-conscious users and future billing. The verified review engine (pillar 5) is its flagship consumer: every review is a metered multi-seat workload.
  ↳ Metering landed: `loom telemetry usage` reads a per-run, per-tool ledger from `{loom_dir}/telemetry/usage.db`. Measurable now: `resume` (provider usage, per turn), `acp` (protocol usage: `loom acp run` + daemon dispatch), `knowledge-extract` (provider usage). Recorded as **unavailable** (no count from the external agent): `workflow` dispatch (CLI + TUI embedded pane) and `loom exec`. The TUI Cost tab renders the ledger. Only a TerminalLaunch run stays invisible (Loom mediates no turn). Pillar 4 remains post-1.0 and gated on pillars 1–3.

### 5. Verified Review Engine *(post-1.0, gated on 2; the pillar-4 demand driver)*

When a session ends, agents that did not write the change re-do the important part blind; a sandbox labels every finding with what it established (`proven` / `suite_green` / `unverified` / `could_not_run` / `refuted`); one fix PR carries only verified patches; a lesson is written from each proven finding and injected into the next session touching that file; a scoreboard tracks which agent is right on which kind of task, at what cost. Conifer Parallax proved this loop is the thing people pay a gateway for. Loom already owns every stage's substrate — capture (`loom-sessions`), seating and outcomes (`loom-routing`), blind dispatch (`loom acp run`), worktree isolation (`loom-parallel`), test execution (`loom-runtime`), PR creation (`loom-trackers`), lessons (`loom-knowledge` + `loom-hindsight`). The two missing pieces are the review orchestration itself (a new `loom-review` crate) and the CI-tested container sandbox, which is pillar 2. Reviewers are existing registered agents dispatched over ACP — Loom does not build a reviewer model. Full build spec, MVP→V2 sequencing, and commercial framing: [docs/plan/LOOM_VERIFIED_REVIEW_PROPOSAL.md](docs/plan/LOOM_VERIFIED_REVIEW_PROPOSAL.md).

## Non-Goals

- **Horizontal daemon scaling.** Investigated; local-first is the design. Don't revisit without new evidence.
- **Electron/GUI client.** The TUI is the reference frontend; UIs consume Loom via the protocol/MCP instead.
- **Building another coding agent.** Loom orchestrates tools; it does not become one.
- **Chasing orchestration-UI competitors feature-for-feature.** Consume their good ideas; stay the infrastructure layer.

## Open Questions

Decisions that change the plan, in order of when they bite:

1. **License for commercial features** — separate closed repo, BSL for team-tier crates, or pure hosted-service (SaaS) model with everything else MIT?
2. **1.0 target** — what date/feature set earns the protocol-stability promise? (Proposal: pillars 1–3 complete = 1.0.)
3. **Cloud posture** — self-hosted-first (customer runs daemon, we sell control plane) vs SaaS-first (we host). Self-host-first fits local-first and the security story.
4. **Pricing anchor** — per-seat team pricing vs per-daemon/host. Conductor anchors per-user at $50–60/mo; Loom's infra depth may support per-host with unlimited seats.
